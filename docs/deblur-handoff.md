# 被写体ブレ補正：作業の引き継ぎ

2026-10-24 時点。ブランチ `claude/project-thread-fw5ryw`（`claude/subject-deblur` の続き。`claude/kind-hopper-jnlyd3` の a84be3b から分岐）。公開版には未反映。

## ねらい（依頼）
- シャッター速度による被写体ブレ（手だけ速く動いてぶれる、など。手ぶれ補正ではない）を補正する。ぶれている所だけ直す。
- 実用に耐える自然さ。極端なブレ（回るスカートなど）までは求めない。重くてよい、「残り○%」のバーを出す。
- 実写真で 100% 拡大して確かめる。数値だけで合格にしない。暗所補正（ノイズ除去・明るさ）・美肌など・書き出しと重ねて確かめる。
- ユーザーの判断（2026-10-25）：**AI（学習済みモデルを端末内で動かす）で進める**。初回に数十MBのダウンロードがあってよい。

## いまの仕組み
編集画面の「自動補正 → 動いた手・髪のブレを直す → 被写体ブレの補正」（ディテールにも同じスライダー）。値は `adj.deblur`（0〜100、50 で標準の強さ）。

| ファイル | 役割 |
| --- | --- |
| `deblur.js` | 計算（DOM なし）。3 段（1/4 → 1/2 → 元の大きさ）で、区画に分けて AI に通す（1 区画 1 回。直した明るさの分だけを使う）・ゆるやかな変化を除く・平らな所を抑える（`deblurResidual`）、差分を元の大きさに引き伸ばして足す（`applyResidual`） |
| `deblur-worker.js` | Worker。モデルを読み込み（初回 36MB）、WebGPU があれば GPU で、なければ CPU の Worker（`deblur-infer-worker.js`）をいくつか作って区画を分けて渡す |
| `deblur-photo.js` | 画面側。写真を縮めて Worker に渡す（`deblurResidualFor`）、差分と細かい粒を足す（`finishCanvas`・`finishBand`） |
| `vendor/ort/` | ONNX Runtime Web 1.30.0（MIT。WebGPU 版のみ。WebAssembly 27MB） |
| `vendor/deblur/nafnet-gopro-w32.onnx` | NAFNet GoPro width32（MIT）を ONNX にしたもの（36MB、重みは半精度） |
| `app.js` | `enhanceSource`：暗所補正（粒なし）→ AI の差分 → 差分と粒を足す。途中の結果を取っておき、ブレ補正の強さだけを変えたときは AI を動かし直さない。計算中は前にできた写真を見せる |
| `fullres.js` | 元の大きさの書き出し。暗所補正を帯ごとに当てたあと、編集中に求めた差分を引き伸ばして足し、粒を足す |

- 順番：ノイズ除去 → 明るさ → **ブレ補正** → 細かい粒（粒の後に当てると粒が筋になる）→ 美肌・修復・ブラシ → GPU の調整 → 書き出し。
- AI に通す大きさは**元の写真の大きさで決める**（`deblurSize`。長い辺 1600 まではそのまま、3200 以上は半分）。編集用の写真で 1 回だけ AI を動かし、その差分を書き出しでも使う（書き出しで AI を動かし直さない）。
- `sw.js`：`vendor/` は、キャッシュにあればそれを使う（モデル・WebAssembly を毎回ダウンロードしない）。キャッシュの名前を v31 に。

## 砂嵐（壊れる区画）の原因と直し方
- NAFNet GoPro は、ある種の入力で途中の値が暴走して色の砂嵐になる（エンコーダー最深段のチャンネル注意 SCA が数百に）。ほんの少しノイズを足すだけで壊れる・壊れないが入れ替わるので、入力の工夫（反転・明るさ倍など）では防げない。屋外の普通の写真でも 165 区画中 7 区画が壊れた。
- **途中の値を、普通の写真で出る範囲に止める**：全ブロックの 6 か所（SimpleGate の後・SCA・SCA を掛けた後・1 つ目の残差の後・2 つ目の SimpleGate の後・出力）で、チャンネルごとの最小・最大を普通の写真 8 枚（屋外・明るい舞台、158 区画）で測り、幅の 25% の余裕をつけて止める（`scripts/deblur-proto/clampnet.py`・`calib.py`）。IMG_9345 の 1/2 で壊れる区画が 31/77 → **0/77**。範囲の測定に使っていない IMG_9499 では、止めても結果はほぼ同じ（差の最大 0.014、中央値 0.0003）。
- それでも残る細かい格子（カーテン）・胸の肌の木目のような筋は、
  1. **左右反転したものも AI に通し、2 つで向きが合う直しだけ（小さい方）を残す**（AI の癖は反転すると向きが変わる）。1.36.2 でやめた（下の「AI を 1 回に」。明るさの分だけを使えば要らなかった）
  2. **直す量を、まわりの明るさのばらつき（縮めた絵で約 6 画素の範囲）× 2.5 までに抑える**（平らな所・肌はほぼ直さない）
  で消えた。手・顔・髪のくっきりさはほぼそのまま。
- ノイズ軽減を使わずに（暗く、ざらついたまま）AI に通すと、胸・手に赤い格子が出た（IMG_9345 の元の写真）。ノイズ軽減が 50 より弱いときは、**AI に渡す縮めた絵だけ先にノイズを取る**（`denoiseSmall`。暗所補正と同じノイズ除去。直した差分は、ノイズを取る前の写真に足す）。格子は消え、顔はくっきりする。
- **3 段で直す**（`deblurResidual2`、`levels = 3`）：1/4 → 1/2 → そのままの順に、前の段の差分を足した絵をもう一度直す。差分の和を使う。2 段で手・袖口などがくっきりし、3 段目（1/4）で前に伸ばした手の指の輪郭がもう少し締まる（IMG_9345）。1/4 の段は区画が少なく、時間は 2 段とほぼ同じ。前に伸ばした手・胸の手・袖口・フリル・脚の飾りが 1 段よりくっきりする（IMG_9345・9395・9316・9242・9328 で確認）。時間は 1 段の約 1.3 倍。
  - 2 段の和をそのまま足すと、頬のやわらかい光の境目が角ばった三角の形になった（IMG_9395）。**和も、元の絵の直してよい量（1 段と同じ上限）までに抑える**と、境目はやわらかく戻り、手・顔のくっきりさはほぼ残った。上限を 1.5 倍にすると角ばりがまた出て、顔が絵のようになった（不採用）。
- AI は全体を少し暗く・色を少し変える（GoPro で学習した癖。IMG_9345 で平均 -1〜-2.4 階調）。差分から広い範囲（縮めた絵で 20 画素くらい）のゆるやかな変化を取り除いた（平均の差 0.04 階調以下に）。

## AI が直せない、なだらかなにじみ（逆畳み込み、1.26.0）
- 依頼（2026-10-25）：暗い舞台の顔（IMG_9313）で、あご・前髪・目・歯の輪郭がにじんで解像度が低く見える。「シャッタースピードが短いときの写真のように」。
- 顔は 10〜20 画素にじんでいる（縦の動きとピントのぼけ）。AI（NAFNet）はこのなだらかなにじみをほとんど直せない（直すのは数画素の細かいブレ）。
- **ぼけの形をガウスぼかし（縮めた絵で標準偏差 2.5、長い辺 2592 のとき。大きさに比例）と仮定して、Richardson–Lucy で 12 回戻す**（`deconvResidual`）。輝度だけ。AI の差分に足す（`deblur-worker.js`）。強さは「被写体ブレの補正」のスライダーに合わせて変わる。
  - 戻した値は、まわり（5×5）の最小〜最大の幅の 3 割までしかはみ出させない（白い縁・黒い縁・輪郭に沿った波の線を作らない）。
  - ぼかした絵の明るさの差（傾き × ぼけの幅）が 0.03 より小さい所には効かせない（その 2 倍で全部）。直す量は、まわりの幅の 3 割まで。肌のなだらかな所・ノイズを取った後のムラは育てない。
- 試してやめたもの：Wiener（周波数で割る）は、輪郭に沿った波の線と、肌の泡のような模様が出た。元の大きさで σ5 は肌がまだらに。縦の動き（直線のブレ）を仮定すると 9313 のあごはよく締まるが、向きと長さを自動で推定する方法（微分の自己相関・輪郭の幅を向きごとに測る）は、ノイズを取った後の小さな段差に引っぱられて当てにならなかった。σ3・20 回以上は頬が面で塗り分けたような絵になる。
- **AI の差分と「直してよい量」（gateMap）を分け合う・変える量はその画素の明るさの 6% まで**（`addDeconv`）。ブレの大きな IMG_9345 で、ブレたままの目の縁だけが戻って、目が黒い切り抜きのように不自然になった（ユーザーの声「これだけ不自然。特に目」）。分け合うだけでは目は変わらず、明るさに比べた上限を足して、目は今の公開版に近い自然さに戻った。9313 のあご・歯のくっきりさは少し弱まるが残る。
- 時間：縮めた絵（2592×1728）で 10 秒くらい（AI の 3 分に比べて小さい）。

2. 前に伸ばした手のような大きなブレは、3 段にして良くなったが、30 画素を超えるものは直りきらない（極端なブレは対象外）。IMG_9395 の頬の光の境目は、抑えたあとも少しくっきりめ。

## 人物だけに・肌のなめらかな所は弱く（1.35.4、2026-10-27）

ユーザーの声「おまかせ＋ブレ補正＋髪・服をくっきりでめっちゃガサガサ」「顔をズームするとザラザラ」。
アプリと同じ処理を 1 段ずつ書き出して（9321・9348・9365）、原因を切り分けた:

- いちばん大きいのはブレ補正。ピントの外れたカーテンのひだを AI がブレと見て縁をギザギザにし、肌ではノイズ除去の後のゆるい段差を
  AI と逆畳み込みが「直して」まだらな面にしていた（9348 の頬が特にひどい）。くっきり（全体 AI）の差分は小さい（肌で標準偏差 0.5/255）
- そのうえに、暗所補正の粒（grainFor、2.7 くらい）が乗って、顔を拡大すると砂のように見えた

直し方:
- `subjectWeight`（deblur.js）: personSeg の地図を 1.2% 広げてぼかしたもの × 肌（segParts の 2・3）のなめらかな所は 0.15。
  肌の中でも、ぼかした明るさの傾きが 0.015〜0.035 以上の所（目・口・鼻・あごの輪郭）はそのまま。差分に掛ける（deblur-worker.js、addDeconv の後）。
  人物が見つからない写真・AI が使えない端末は今までどおり全体。重みが 0 の区画は AI に通さない
- 顔の肌の粒は半分（restoration-lowlight.js の FACE_GRAIN。planTone が顔の肌の地図 tone.face を持ち、applyTone・addGrain で弱める）。
  0 にすると肌がのっぺりして「イラストっぽい」に戻る

## AI を 1 回に（1.36.2、2026-11-04）

ユーザーの依頼（2026-11-02）「OSS など外部ツールを使って精度・速度が上がるなら使って」。iPhone でいちばん時間がかかるのはブレ補正の AI
（クラウドの 4 コアで iPhone として IMG_9348、ブレ補正 50・くっきり 50・ぼかし: 仕上げ 307 秒のうち、暗所補正 44 秒、ブレ補正 195 秒、全体 AI 49 秒。書き出しは別に 48 秒）。

- 前は区画ごとに、そのままと左右反転の 2 回 AI に通し、R・G・B ごとに向きが合う直しの小さい方を残していた。反転をやめただけだと、白い服・肌に緑・ピンクの色のむらが出た。
- **AI が直した明るさ（0.299R + 0.587G + 0.114B の差）だけを、R・G・B に同じだけ足す**（`deblurResidual` の `one`。逆畳み込みはもとから明るさだけ）。
  色のむらは出ず、7 枚（9316・9395・9345・9242・9328・9348・9365）の顔・手・髪・フリル・レースを 2 倍で見て、今までのものと見分けがつかない。
  白いフリルの縁の黄緑・橙のにじみ（IMG_9242 の脚の飾り）は、今までより少ない。
- 直す量は平均で 1.15〜1.27 倍（2 つの小さい方を取らなくなったため）。直してよい量（`gateMap`・`limitResidual`）・人物だけ（`subjectWeight`）はそのまま。
- 時間（iPhone として IMG_9348、ブレ補正 50・くっきり 50・ぼかし。今までのものと続けて 1 つずつ測った）: ブレ補正 195 秒 → 112 秒、仕上げ全体 307 秒 → 227 秒。パソコンでは CPU の Worker が 2 区画ずつ動かしていた（1 つ約 270MB）のが 1 区画ずつ（約 190MB）になる。
- 比べた写真: プロジェクトの `deblur-fast/`。計算の版 `CALC.db` = 2（前に開いた写真のブレ補正は、一度だけ計算し直す）。

外部のツールで試して、使わなかったもの（数字はクラウドのブラウザー、WebAssembly 1 本、NAFNet の 256 区画 1 つ 1.50 秒）:
- int8 量子化（onnxruntime の `quantize_static`）: WebAssembly の int8 の行列計算は float の 1.2 倍ほどしか速くなく、全部の畳み込みで 1.57 秒（遅くなる）、32×32 の段だけで 1.34 秒。差分（アプリが使うもの）の誤差が 66〜95% で使えない。
- ONNX Runtime 1.31・CPU だけの版: 速さ・メモリは同じ（読み込みが速いだけ）。`vendor/` を変えると端末は全部のモデルを取り直す（`VENDOR_CACHE` は 1 つの指紋）。
- モデルの組み替え（LayerNorm の式の置き換え、その掛け算を次の 1×1 の畳み込みに入れる、など。結果は 1e-5 まで同じ）: 3% だけ。時間の大半は 1×1 の畳み込み。
- Worker・スレッドを増やす: スレッドはクロスオリジン分離が要り、iPhone は速いコアが 2 つなので速くならない見込み。Worker を増やすとメモリ不足で落ちるおそれ。
  WebGPU は iPhone で 4 分以上固まった（1.35.3）。どちらも実機で確かめずには変えない。
- 別のモデル: NAFNet の幅 64 は計算が 4 倍。奥行きの Depth Anything V2 の大きい版は非商用のライセンス。人物の切り抜きの BiRefNet・ISNet は iPhone には重い。
